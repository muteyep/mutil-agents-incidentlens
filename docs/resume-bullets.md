# 简历写法与面试防守

> 当前指标以 **RCAEval RE2-OB 40 条真实 case** 为主，12 条合成 case 仅用于消融。写简历必须注明"合成评测集"；接入 RCAEval 后替换数字，不要把 100% 写成生产准确率。

## 项目标题

> **IncidentLens｜多智能体故障根因分析系统**　2026.11–2027.01
> 技术栈：Python / LangGraph / SQLite / Pydantic / DeepSeek / Streamlit

## 五条 bullet

1. **架构**：设计 Supervisor + 指标/日志/链路三专家 + Critic 的多 Agent 架构，三路并行取证、结构化回传，解决单 Agent 长链路上下文膨胀问题。
2. **算法**：提出"LLM 取证、规则定因"的神经符号式设计：根因排序由证据图加权分与因果惩罚（`self − 0.5 × callee`）决定，LLM 只生成解释；18 条 case 上 multi R@1 100%，单 Agent 72.22%，加权排序 33.33%；RCAEval 真实样本（checkoutservice CPU）端到端正确（Bootstrap 95% CI 见评测报告）。
3. **可靠性与治理**：基于 LangGraph Checkpoint 实现断点续跑，高风险处置通过 `interrupt()` 挂起、`Command(resume=...)` 恢复；加入步数/工具/时间三重预算、无进展循环检测、证据 ID 审计。
4. **安全**：针对日志中的间接 Prompt Injection，设计模式扫描 + 证据降权 + 标记机制；注入样本不改变根因结论，配套 37 个测试。
5. **评测**：搭建 R@1/R@3/MRR/故障准确率/延迟/成本六类指标，实现 multi / single / no_causal / multi_llm 四组对照与 Bootstrap 95% 置信区间，定位"多源缺失"和"victim bias"两类失败模式。

## 面试防守表

| 追问 | 回答要点 |
|---|---|
| 为什么不让 LLM 直接定根因？ | 不可复现、不可解释、无法消融；LLM 只抽取，排序用图和统计 |
| 因果惩罚的 0.5 怎么来的？ | 先验权重；0.3/0.5/0.8 都跑过，0.5 在合成集最稳；真实数据要重调 |
| 70% 怎么来的？ | RCAEval RE2-OB 40 条分层抽样，全分辨率 metrics+logs，Online Boutique 拓扑；不是合成集 |
| 多 Agent 协调开销？ | 三路并行，耗时约等于最慢一路；主要开销在汇总 |
| 断点续跑会重复调工具吗？ | 当前恢复状态；工具幂等账本是下一步（如实说） |
| 注入防护会不会误杀？ | 只标记 + 降权，不删除；正常日志无匹配模式 |
| 为什么做 Bootstrap？ | 40 条样本点估计仍不可信，报区间才诚实 |
| 什么时候不该用多 Agent？ | 单源数据、短链路、成本敏感场景 |

## 不要写

- 不写"生产级/高并发/分布式"。
- 不把合成集数字写成真实业务指标。
- 不把 RCLAgent 的递归分治说成原创；说"参考并扩展"。
- 不写"100% 准确率"而不注明数据集。
